# Day 18 — Versioning Datasets and Models with Git Branches and DVC

## Overview

Part of the *100 Days of MLOps* challenge. This day versions the same
fraud-detection pipeline on two different dataset states:

- `main` is tagged `v1.0` with the baseline dataset and model;
- `v2-improved` replaces the tracked raw dataset with `transactions_v2.csv`,
  retrains the pipeline, and commits the new DVC metadata.

Switching back to `main` must restore the original dataset and model on disk by
combining Git checkout with DVC checkout.

The `fraud-detection` project lives at `/root/code/fraud-detection/`.

## Task

The environment:

| Fact | Value |
| --- | --- |
| Project | `/root/code/fraud-detection/` |
| Pipeline | `process_data` → `split_data` → `train` |
| Baseline data | `data/raw/transactions.csv`, tracked by `data/raw/transactions.csv.dvc` |
| Improved data | `data/raw/transactions_v2.csv`, pre-staged and gitignored |
| Git state before task | clean `main` with initial pipeline already run |
| Constraint | Do not delete `transactions_v2.csv` |

Acceptance criteria:

- On `main`, the current state is tagged `v1.0`.
- A branch named `v2-improved` holds the v2 state: the tracked dataset carries
  the contents of the v2 file, re-tracked with DVC; the pipeline has been re-run
  so `models/model.pkl` is retrained and versioned alongside the dataset; and
  the changes are committed.
- Back on `main`, the v1 dataset and model are restored on disk, matching the
  hashes recorded by the `v1.0` tag.
- The DVC extension's **DVC TRACKED** section reflects the tracked dataset and
  model for the checked-out branch.

## Background: Git vs DVC responsibilities

### Git stores metadata, DVC stores data

Large files such as CSVs and `model.pkl` should not be committed directly to Git.
DVC tracks them through pointer files:

- `data/raw/transactions.csv.dvc` records the hash of the raw dataset;
- `dvc.lock` records hashes for pipeline dependencies and outputs, including
  processed CSVs and `models/model.pkl`;
- local `.gitignore` files generated by DVC keep the large files out of Git.

That means a branch switch updates the *pointers* in Git, but DVC may still need
to restore the actual file contents from its cache.

### Why `dvc checkout` is needed after `git checkout`

`git checkout main` restores Git-tracked files such as `dvc.lock`,
`transactions.csv.dvc`, `dvc.yaml`, and source code. It does not necessarily
rewrite every DVC-managed binary/data file on disk to match those pointers.

After switching branches, run:

```bash
dvc checkout
```

This tells DVC to make the workspace match the current Git-tracked DVC state.

## Solution

Run all commands from `/root/code/fraud-detection`.

### 1. Verify the baseline before tagging `v1.0`

Check that the repository is on `main`, clean, and that DVC reports no drift:

```bash
git status
git branch --show-current
dvc status
dvc data status
```

Expected state:

```text
On branch main
nothing to commit, working tree clean
```

```text
Data and pipelines are up to date.
```

```text
No changes.
```

Inspect the lockfile to confirm that the baseline pipeline already produced the
dataset, processed files, and model:

```bash
cat dvc.lock
```

For the baseline observed in this exercise, the important hashes were:

| Path | md5 | size |
| --- | --- | --- |
| `data/raw/transactions.csv` | `c4dd797a1451653b3cb76a8bb7b2b4d9` | 379 |
| `models/model.pkl` | `331af74a93fb4992f3e5b81b98d5e52f` | 67737 |

### 2. Tag the baseline

Once `main` is verified, create the tag:

```bash
git tag v1.0
git tag -l
```

### 3. Create the v2 branch

```bash
git checkout -b v2-improved
```

### 4. Replace the tracked dataset with the v2 contents

The task provides `transactions_v2.csv` as a source file, but the pipeline still
reads `data/raw/transactions.csv`. Copy the v2 contents into the tracked path
without deleting the original v2 file:

```bash
cp data/raw/transactions_v2.csv data/raw/transactions.csv
```

Then update the DVC pointer for the raw dataset:

```bash
dvc add data/raw/transactions.csv
```

DVC updates `data/raw/transactions.csv.dvc` with the new hash. The large CSV
itself remains gitignored; only the `.dvc` pointer is committed to Git.

### 5. Re-run the pipeline

```bash
dvc repro
```

Expected behaviour:

```text
Running stage 'process_data':
Running stage 'split_data':
Running stage 'train':
Trained model on 16 rows
Updating lock file 'dvc.lock'
```

This retrains `models/model.pkl` from the new dataset and updates `dvc.lock`.

### 6. Check what changed

```bash
git status --short
```

Expected Git-visible changes:

```text
 M data/raw/transactions.csv.dvc
 M dvc.lock
```

`transactions_v2.csv` must not be committed. Verify that it is ignored:

```bash
git check-ignore -v data/raw/transactions.csv
git check-ignore -v data/raw/transactions_v2.csv
```

Expected result: both are ignored by `data/raw/.gitignore`.

### 7. Stage only the DVC metadata

Do **not** add `.gitignore` at the repository root; there is no root `.gitignore`
in this project. DVC already created local `.gitignore` files in tracked output
directories.

Stage the changed metadata files:

```bash
git add data/raw/transactions.csv.dvc dvc.lock
```

Confirm the staged files:

```bash
git status --short
```

Expected:

```text
M  data/raw/transactions.csv.dvc
M  dvc.lock
```

### 8. Commit the v2 state

```bash
git commit -m "Add v2 dataset and retrained model"
```

Verify the commit:

```bash
git status
git log --oneline --decorate -3
git show --stat --oneline HEAD
```

The commit should contain only Git-tracked metadata, especially:

```text
data/raw/transactions.csv.dvc
dvc.lock
```

It should not contain the large data/model files themselves.

### 9. Return to main and restore v1

Switch back to the baseline branch:

```bash
git checkout main
```

Then restore the DVC-managed file contents for the `v1.0` state:

```bash
dvc checkout
```

Verify that DVC restored the v1 files:

```bash
dvc status
dvc data status
git status
```

Expected:

```text
Data and pipelines are up to date.
```

```text
No changes.
```

```text
On branch main
nothing to commit, working tree clean
```

## Gotchas

### No root `.gitignore` is needed

This project uses DVC-generated `.gitignore` files inside output directories:

```text
.dvc/.gitignore
data/processed/.gitignore
data/raw/.gitignore
models/.gitignore
```

Trying to stage a non-existent root `.gitignore` fails:

```bash
git add data/raw/transactions.csv.dvc dvc.lock .gitignore
# fatal: pathspec '.gitignore' did not match any files
```

Use the explicit DVC metadata paths instead.

### `transactions_v2.csv` is source material, not the tracked dataset

The task says not to delete `transactions_v2.csv`. It is pre-staged as the new
dataset source and is gitignored. Do not commit it. Copy its contents into
`data/raw/transactions.csv`, then run `dvc add` so the tracked dataset pointer
points to the new content.

### `git checkout` alone is not enough for DVC files

After switching back to `main`, Git restores the metadata but the large DVC
outputs still need to be checked out from the DVC cache:

```bash
git checkout main
dvc checkout
```

Without `dvc checkout`, the workspace may still contain files from the previous
branch.

### Commit DVC metadata, not data blobs

For this task, the v2 commit should contain pointer/lock metadata:

```text
data/raw/transactions.csv.dvc
dvc.lock
```

It should not contain:

```text
data/raw/transactions.csv
data/raw/transactions_v2.csv
data/processed/*.csv
models/model.pkl
```

Those files are ignored and managed by DVC.

## Command cheat sheet

```bash
# baseline checks
git status
git branch --show-current
dvc status
dvc data status
cat dvc.lock

# create baseline tag
git tag v1.0

# create v2 branch
git checkout -b v2-improved

# replace tracked dataset content and retrack it
cp data/raw/transactions_v2.csv data/raw/transactions.csv
dvc add data/raw/transactions.csv
dvc repro

# stage and commit only DVC metadata
git add data/raw/transactions.csv.dvc dvc.lock
git commit -m "Add v2 dataset and retrained model"

# return to v1
git checkout main
dvc checkout
dvc status
dvc data status

# compare refs
git show v1.0:dvc.lock
git show v2-improved:dvc.lock
```

## Further reading

- `dvc add` — <https://doc.dvc.org/command-reference/add> — track a data file or
  directory with DVC and generate/update its `.dvc` pointer.
- `dvc repro` — <https://doc.dvc.org/command-reference/repro> — rerun pipeline
  stages whose dependencies changed and update `dvc.lock`.
- `dvc checkout` — <https://doc.dvc.org/command-reference/checkout> — restore
  DVC-tracked files in the workspace to match the current Git-tracked state.
- `dvc data status` — <https://doc.dvc.org/command-reference/data/status> —
  inspect changes to DVC-tracked data not yet committed through Git.
